# Kopilot v0.3.0 — Ship & Client-Install Readiness

Date: 2026-08-20
Status: approved by standing instruction (autonomous run); Riadh may redirect at any time.

## Goal (definition of done)

A client can install Kopilot v0.3.0 from published, versioned artifacts —
`helm install` from an OCI chart on ghcr.io backed by a versioned container
image — and the exact path they would follow has been verified end-to-end on a
fresh local kind cluster in this run. A GitHub Release with honest notes
exists. Docs and site describe the verified path and nothing else.

## Out of scope

- Hosted control plane, multi-replica approval HA (documented limit stays)
- Site framework rewrite (ROADMAP: not in window)
- Breaking rename of `kopilot` package/API groups (needs migration plan)

## Phase 1 — Release plumbing

- `release.yml`: add a `helm-publish` job on `v*` tags — `helm package` +
  `helm push` to `oci://ghcr.io/kopilot-ai/charts` using GITHUB_TOKEN
  (packages: write already granted).
- `ci.yml`: add `helm lint` + `helm template` check.
- Version bump to 0.3.0: `pyproject.toml`, `Chart.yaml` (version + appVersion),
  `src/kopilot/__init__.py` (single source), CHANGELOG `[0.3.0]` section.

## Phase 2 — Durable approvals (SQLite)

- `ApprovalStore` gains a SQLite backend (stdlib `sqlite3`, same lock
  discipline) selected by `APPROVALS_DB_PATH`; unset keeps today's in-memory
  behavior. Same interface, same TTL/retention semantics, transitions audited.
- Helm chart: `APPROVALS_DB_PATH=/data/approvals.db`, emptyDir at `/data` by
  default, `persistence.enabled` values switch for a PVC.
- Honest-limits language updates from "in-memory, does not survive restart"
  to "single-replica; durable when APPROVALS_DB_PATH is set (Helm default)".
- TDD: parametrize existing store tests over both backends + restart-survival
  test (new store instance on same file sees pending requests).

## Phase 3 — AISkill CRDs load for real (serve mode)

- `on_aiskill_create/update`: build a skill definition from spec
  (name, display_name, description, system_prompt, documentation) and
  register into the process-global SkillRegistry; delete handler unregisters.
- Only effective in `kopilot serve` (operator thread shares the process);
  standalone `kopilot operator` sets status honestly
  ("Registered — served by the serve process").
- Tests: handler ↔ registry integration with mocked kopf payloads.
- README/site: move AISkill from "planned" to documented, with the
  serve-mode caveat stated.

## Phase 4 — E2E install proof (kind + podman)

1. `podman machine start`; `scripts/setup-local-k8s.sh` (kind).
2. Build image locally, `kind load`.
3. `helm install` with a real LLM provider (Gemini key from 1Password/env;
   fallback: any available provider), `API_AUTH_TOKEN` set.
4. Verify: `/health`, `/skills`, submit read-only task, submit a destructive
   prompt → approval appears → approve → executes; restart pod → pending
   approvals survive (Phase 2 proof).
5. Apply an AISkill CRD → appears in `/skills` (Phase 3 proof).

## Phase 5 — Docs truth pass

- README Quick Start leads with the client path:
  `helm install kopilot oci://ghcr.io/kopilot-ai/charts/kopilot --version 0.3.0`
  plus the pip-from-source path for local dev.
- Site `docs/quickstart.html`, `deployment.html`, `configuration.html`,
  `concepts.html` synced. Voice per BRAND.md; humanize sweep on all prose.

## Phase 6 — Ship

- Commit series on main (small, honest messages), push.
- Tag `v0.3.0`, push tag; watch release workflow; confirm
  `ghcr.io/kopilot-ai/kopilot:v0.3.0` and the OCI chart are pullable
  from a clean directory.
- `gh release create v0.3.0` with notes distilled from CHANGELOG.

## Phase 7 — PyPI (conditional)

- If a PyPI token exists in 1Password: publish `kopilot` 0.3.0
  (and evaluate `kopilot` name availability), add trusted-publishing workflow.
- Else: single follow-up action listed for Riadh in the final report.

## Risks

- ghcr chart push may need package visibility flip to public (one API call).
- kind/podman E2E with an LLM depends on an available API key; the install
  path proof does not strictly require LLM correctness, only that the agent
  serves, loads skills, and gates approvals.
- LangChain/langgraph dependency drift: suite green today pins nothing new.
